# Agent 内容质量 Benchmark v1

本目录提供 Guidance、Employee、Coach 三类 Agent 的合成数据试运行。案例和标签均为虚构、待审，**不能代表专家标注或真实 HR 场景质量基线**。当前质量报告固定 `release_eligible=false`。

## 数据和入口

- `datasets/synthetic_v1.jsonl`：30 个 UTF-8 合成案例，每类 10 个。每行含 `case_id`、`provenance=synthetic`、`agent`、`locale`、`state`、`manager_turns` 和 `tags`。
- `labels/synthetic_v1_draft.jsonl`：与案例一一对应的待审事实和建议分数范围，固定 `review_status=draft_unreviewed`。此文件不输入独立 Judge。
- `generate_synthetic_v1.py`：确定性重建上述文件；只有要更新首版数据时才运行。
- `run_quality_bench.py`：先验证数据，再使用现有生产服务入口运行。`--validate-only` 不访问数据库或模型。
- `expert_review_template.md`：双人独立复核的数据格式与流程。

在项目根目录用 Python 3.11 执行结构校验：

```powershell
python eval/run_quality_bench.py --validate-only
python -m unittest tests.test_agent_quality_bench -v
```

## 隔离运行环境

真实运行前，安装 `backend/requirements.txt`，使用项目支持的真实模型、Embedding 和 Reranker 配置。`eval/compose.yml` 创建独立 PostgreSQL 和 Redis 卷，仅绑定本机端口。设置未提交的随机密码：

```powershell
$env:EVAL_DB_PASSWORD = '<独立数据库密码>'
$env:EVAL_REDIS_PASSWORD = '<独立 Redis 密码>'
docker compose -f eval/compose.yml up -d
```

在当前 PowerShell 会话设置 `DATABASE_URL` 与 `DATABASE_ADMIN_URL` 为 `postgresql://hr_agent:<密码>@127.0.0.1:7244/hr_agent_eval`，设置 `REDIS_URL` 为 `redis://:<密码>@127.0.0.1:7248/1`，并设置 `RUNTIME_DATA_DIR` 为项目下的 `eval/runtime`。可复用 `loadtests/data/kb_raw` 中的合成知识文档作为独立评测知识库的**输入副本**：

```powershell
New-Item -ItemType Directory -Force eval/runtime | Out-Null
Copy-Item -LiteralPath loadtests/data/kb_raw -Destination eval/runtime/kb_raw -Recurse
```

随后在同一隔离配置下运行：

```powershell
python scripts/init_postgres.py
python scripts/ingest_kb.py
```

导入时会调用配置的 Embedding 模型。runner 还会检查数据库名以 `_eval` 结尾、Redis 使用非零 DB、运行数据目录含 `eval`，并要求已索引的知识库非空。不要把生产数据库或生产 Redis URL 用于评测。

独立 Judge 需要 OpenAI 兼容的 chat completions URL，并与所有被测及重试模型使用不同的模型名称：

```powershell
$env:EVAL_JUDGE_URL = '<Judge chat completions URL>'
$env:EVAL_JUDGE_MODEL = '<独立 Judge 模型>'
$env:EVAL_JUDGE_API_KEY = '<Judge 密钥>'
python eval/run_quality_bench.py --confirm-live-model-cost --output eval/results/synthetic-v1.json
```

默认每例运行 3 次，共 90 次案例重放，Employee 案例每次包含两轮回复；还会产生 Judge 调用。先用 `--case guidance_001 --trials 1` 做单例试运行。`--skip-judge` 仅验证工程路径，报告 `quality_scored=false`，不产生质量通过率。任何模型或 Judge 失败都会记录在逐次结果中，不计为通过。

## 判分和报告

确定性规则检查输出 Schema、Coach 四维结果与 Manager 原话、知识库 chunk ID、员工内部评级泄露和明显语言错误；复杂语言质量由独立 Judge 评估。报告保存逐次输出、规则问题、Judge 理由、失败、耗时、Git 版本、模型名称、Prompt/业务配置哈希和知识库构建 ID。`pass_at_1`、`pass_at_3`、`pass_all_3` 只在 Judge 完成时计算，合成数据结果仅用于发现问题。

专家应按模板双人独立标注，保留原始标签和分歧处理记录。完成校准后再建立真实案例基线、Judge 一致率和正式发布门槛。首次版本不会伪造这些结果。
