# Fish S2-Pro：修复 FastAR 实际编译路径

本轮保持原 S2-Pro 权重、vLLM-Omni 0.24.0、PyTorch 2.11.0+cu130 和十路容量，只修复 FastAR 的编译实现。真实 RTX 4090 上的独立数值验证通过：批量 1～10 的 FastAR 解码微基准为 eager 的 **1.11～1.13 倍**，本次检查的 hidden、logits、KV 与采样结果均无差异。

**这是 FastAR 子模块结果，不等于整条 TTS 提速 11%～13%。** 相同十路工作负载的三轮 HTTP 对照，总音频吞吐实测为 **11.852 → 12.164 音频秒/墙钟秒（+2.63%）**；轮间区间重叠，不能将这一短测均值视为稳定 SLA 或增加并发上限的依据。

## 根因与修复

原 `_setup_compile()` 编译 `model.forward`，残差码本生成实际却由 `_run_model_one()` 直接调用 `model.forward_one`；“编译已启用”的日志并不能证明热路径得到加速。

[补丁](../fish_tts/patches/vllm_omni_0_24_fish_fast_ar_compile.patch) 由 [Dockerfile](../fish_tts/Dockerfile) 在固定上游源码哈希检查后应用，主要变化：

- 编译对象和实际调用统一为 `model.forward_one`，使用动态形状；预热按最大容量预分配缓存，覆盖单路、小批量和最大批量，减少首次用户请求时的编译及重分配。
- KV 写入从整数位置赋值改为单位置切片 `.copy_()`，避免每个 `cache_pos` 被特化为一个新图。仍只写当前码本位置，不改变缓存内容或注意力范围。
- 开启 `emulate_precision_casts=True`，同时关闭 `pattern_matcher`，保留原 eager 的 BF16 舍入边界；不以改变计算精度换取性能。
- 明确关闭本编译路径的 `triton.cudagraphs`。采样循环仍在 eager 路径，各用户继续使用独立生成器；不把 RNG、可变缓存或整个采样循环捕获进 CUDA Graph。
- 编译器不支持时记录失败并回退 eager；CUDA OOM、非法内存访问等设备错误不被当作正常编译回退吞掉。验证器不把回退后的可用性误记为加速成功。

模型权重、音色、采样参数、文本内容、普通音频块和十路配置没有因本补丁调整。

定位发现，PyTorch 的 FX 模式会将 `mm → BF16 舍入 → residual add` 改写为 `addmm`，改变中间舍入，误差在四层累积。这里关闭的是本 FastAR 编译句柄的模式重写，不是全局关闭 Inductor。动态形状也不保证完全不特化：达到默认 8 次重编译上限会回退 eager，见 [PyTorch 2.11 文档](https://docs.pytorch.org/docs/2.11/generated/torch.compile.html)。本次通过动态切片修复，没有提高上限。

## 真实权重数值验证

[验证器](../scripts/verify_fish_fast_ar.py) 在独立进程内加载真实 FastAR 的全部 27 个参数项，不加载整个 SlowAR/DAC。使用唯一临时文件 rendezvous 建立单 rank 环境，退出时销毁本进程的通信组，不复用在线服务的通信端口。

最终运行序列为 `1→10→2→9→3→8→4→7→5→6→1`，连续两轮；每次覆盖 `cache_pos=0..9`，使用与生产一致的 `[capacity, 11, hidden]` 缓冲布局并复用已预分配的 KV。测试使用合成隐藏状态而非真实用户数据。

| 检查 | 实测结果 |
|---|---|
| hidden、logits、已写 KV | 220 个检查点全部通过，各类最大绝对误差均为 0 |
| 编译句柄调用 / 真实 Inductor 图执行 | 1500 / 1500，未执行图的调用为 0 |
| 捕获图数 | 4 |
| 重编译上限 | 验证期间局部启用 `fail_on_recompile_limit_hit=True`，未触顶 |
| 逐用户 RNG | 两轮所有用户均推进，状态与 eager 一致 |
| 用户顺序反转 | 还原用户顺序后的码本及 RNG 状态均一致 |
| eager / compiled 采样码本 | 两轮均 100% 一致 |

验证器默认 `atol=rtol=0.02`，但以上“零误差”来自实际记录，而非仅满足该容差。严格重编译检查只在验证进程的局部上下文生效，没有提高生产重编译上限来掩盖问题。

微基准统计预热后每批量 10 次、每次 10 个码本位置的完整解码耗时中位数，交替测量 eager 与 compiled：

| 批量 | eager | compiled | 速度比 |
|---:|---:|---:|---:|
| 1 | 12.00 ms | 10.80 ms | 1.111× |
| 4 | 13.27 ms | 11.85 ms | 1.120× |
| 8 | 13.43 ms | 11.96 ms | 1.123× |
| 10 | 13.48 ms | 12.05 ms | 1.119× |

所有批量 1～10 均有测量，范围为 1.111～1.130×。这对应约 10%～12% 的子模块耗时下降，不应把速度比直接写成等幅耗时下降。计时不包含采样、SlowAR、DAC、HTTP、应用排队或浏览器缓冲；图执行统计也带有少量 Python 观测开销。

## 整段音频与十路 HTTP 对照

固定合成中文文本、`employee-natural` 音色、种子 47001、1024 token 上限，更新前后非流式 WAV 均为 10.681179 秒、44.1 kHz、单声道 PCM16，942124 字节，`cmp` 逐字节一致。两者 SHA-256 均为 `9018a80f4f94761dac1f229f34dd1c6a7d937b0b72c08837943532f8b9bb27f2`。这是一个固定音频样本的回归证据，不代表任意并发调度下的音频都会逐字节相同，也不替代主观听感评测。

十路流式 HTTP 使用与基线相同的 182 字正文、逐请求编号和种子、2048 token 上限，预热后三轮：

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| 请求成功 | 30/30 | 30/30 |
| 三轮总音频吞吐（音频秒/墙钟秒） | 11.852 | 12.164 |
| 单轮吞吐范围 | 11.570～12.106 | 11.541～12.544 |
| 三轮各自 P95 首音 | 0.676 / 0.651 / 0.596 秒 | 0.954 / 0.783 / 0.598 秒 |
| 模拟连续播放通过 | 30/30 | 30/30 |

吞吐取三轮总音频时长除以三轮墙钟时长之和，所有正式轮次均计入，不挑选最快轮。候选首音没有稳定改善；FastAR 子模块收益被 SlowAR、DAC、排队和传输等成本摊薄，不能承诺整轮等幅加速。

候选另有单独 `candidate-warm10.json` 冷预热记录：首音 P95 为 8.706 秒，日志记录了 SlowAR kvcache 的首次 Triton JIT；该轮不混入稳态对照。新容器 FastAR 启动预热约 20 秒，首次服务重建还涉及其他模型加载和编译，不等同于日常请求耗时。

## 多用户分句播放与取消

采用真实 Fish HTTP、`FishTtsService`、进程内 `SpeechWebSocketHub` 和合成播放接收端，保持 1.4 秒起播缓冲、最长允许中断 0.1 秒、共同连续播放至少 10 秒的原判定：

- 四用户：4/4 完成，最长共同连续播放 17.461 秒；取消其中一人后其余 3/3 继续收到音频并完成。
- 十用户连续三轮：30/30 完成，最长共同连续播放分别 17.276 / 17.411 / 17.316 秒，所有用户模拟断流均为零。
- 十用户的三轮取消场景：其余 27/27 用户在同伴取消后仍收到音频并完成；PCM 隔离、名额释放及缓冲等待探针均通过。

这些是实际模型加应用内合成接收端测试，**不是多台浏览器或真实音频设备实测**，不包含 Redis、数据库、LLM、WebSocket 网络延迟和主观听感，也不是长时稳定性或更高并发上限证明。没有增加模型/应用名额来获得这些结果。

## 两次失败候选保留为证据

1. **仅改接编译调用仍不成立。** 第一版共 480 次句柄调用，只有 8 次真实图执行，472 次没有执行图；整数缓存位置不断产生特化，触及重编译上限后静默走 eager。当时 `_compile_failed=false`，说明只检查异常标记或编译日志会得到错误结论。
2. **图真正运行不等于数值正确。** 第二版改进动态缓存写入后，520/520 次执行图、仅 4 图且无 graphless 调用，但 80 个数值检查点未通过；两轮采样码本与 eager 的一致率分别约 92% 和 87%。仅模拟精度转换仍不足，后续关闭相关模式改写后才获得最终零误差结果。没有放宽容差让这一版通过。

这些结果分别保存在 `verification-initial-failed.json` 和 `verification-v2-numerical-failed.json`；最终结果为 `verification-passed.json`。
