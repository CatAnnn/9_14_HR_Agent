# Fish S2-Pro：保留首音分段计时，拒绝两项模型候选

本轮接续 [采样去重验证](tts-sampling-optimization-20260906.md)。保持 S2-Pro 权重、vLLM-Omni 0.24.0、FastAR 编译路径、逐用户随机生成器、音色、BF16/FP16 精度、采样参数、十路容量及 1.4 秒播放缓冲不变。不修改 `.env` 或自动开启全站语音。

**本轮没有已验证的模型吞吐提升。** 概率准备整体编译既改变结果又更慢；首次完整 prefill 省传输虽然局部更快且逐值一致，完整 HTTP WAV 却持续不同，已撤回其补丁、测试与 Dockerfile 接线。仓库和运行标签回到本轮原模型基线，只保留压测计时改善及实验记录。

## 已保留的实现

[HTTP 压测脚本](../scripts/benchmark_fish_tts.py) 增加 `response_headers_seconds` 与逐请求 `headers_to_first_audio_seconds`，分别汇总成功请求的 P50/P95，不做百分位相减。未知时间保留 null，空音频和失败请求仍判失败；HTTP 错误体读取失败也不会丢失已收到的状态和响应头时刻。

这两个计时区间是客户端观察值：前者约含请求准备及网络，后者约含排队、模型、编码及网络。服务或代理的响应头发送时机会影响边界，不能当成精确内部阶段耗时，也不是浏览器真正开始播放的时间。

## 已撤回的 prefill 省传输候选

- 试验补丁仅让首次完整、二维、CUDA 同设备、BF16、连续且 storage offset 为零的 prompt embeddings 直接 detach 后返回，避免 GPU→CPU→固定内存→GPU 往返。返回的 pad input IDs 仍独立克隆，audio codes 仍初始化为零，`prefill=None` 和 `prefill_offset` 不变。
- 首次部分 prefill、后续缓存续读、补齐、其他设备、其他精度或布局全部保留原分支。没有修改 builder、缓存内容、SlowAR 数学计算或 DAC。
- 当前 builder 每次生成新的 prompt embedding；音色缓存只保留参考码本，不共享用户 prompt embedding。runner 会把返回结果复制到对应用户的输入缓冲切片。
- 候选曾在固定依赖和原始源码哈希检查后以 `fuzz=0` 构建；完整音频失败后已移除仓库接线，补丁及测试只留在本机结果目录作为证据。

## 已拒绝：把概率准备整体编译

独立 GPU 探针在真实生产布局 `[B,4096][:,:1024]`、BF16、top-k 30、top-p 0.9、温度 0.8 下，对随机、重复值和均匀 logits 进行 33 组检查。虽然沿用了当前精度保护配置，仍有 **25 组改变了采样支持集合**，只有 8 组逐值一致。

批量 1/4/10 的 eager 中位数分别约 0.0844/0.0868/0.0847 ms，编译后约 0.0998/0.0998/0.0996 ms。没有正确性或性能收益，因此**没有把该编译候选加入仓库补丁或部署**，没有降低精度要求来接受差异。

## 真实 GPU 预填充方法检查

从原始与候选源码 AST 提取完整 `preprocess` 方法执行，使用合成 builder 输出，不加载模型权重。63 组检查通过，包括 BF16/FP32、连续/非连续/非零 storage offset、普通/结构化 builder、部分首轮和后续缓存读取、十用户独立数据。新旧输出逐值一致，输入与 RNG 状态不变；部分首轮继续保留相同 pinned CPU 缓存。

下表只计 builder 已返回后这段 `preprocess` 的成本；每组预热，随后交替执行两种实现各 100 次，以 CUDA 同步和墙钟计时取中位数。**不能把该局部比例解释为整个模型提速比例。**

| Prompt token 数 | 原实现 | 候选 |
|---:|---:|---:|
| 128 | 0.920 ms | 0.026 ms |
| 384 | 2.618 ms | 0.024 ms |
| 768 | 5.128 ms | 0.026 ms |
| 1536 | 10.153 ms | 0.026 ms |
| 2048 | 13.553 ms | 0.026 ms |

正常结构化音色请求预计命中新分支：API 的参考帧数估计和编码器都按 44100 Hz/2048 samples 计算，API/worker 使用同一 prompt token 列表构造器；当前禁用 chunked prefill 和 prefix caching。不过本轮未添加服务内分支命中计数，不能把源码预期或合成输入视为真实命中率。

## 完整 WAV 失败，不能用局部一致性替代

固定同一段中文、音色 employee-natural、种子 47001、非流式 WAV，两边都是 884,780 bytes（442,368 个 PCM16 samples）：

| 实现 | SHA-256 |
|---|---|
| 本轮原基线 | `21ea5805f170a1a905af070f0b5845774346b7c0ae8b3f21e8611438aeb9d8a5` |
| 省传输候选首次及预热后重复 | `6eb59a4274d931d17552be38bddeb6deab4d6f4233b2cf633c1f27633770588d` |
| 恢复原镜像后重新请求 | `21ea5805f170a1a905af070f0b5845774346b7c0ae8b3f21e8611438aeb9d8a5` |

候选两次彼此一致，但与基线有 442,108 个 PCM samples 不同，最大整数样本差 60,256，误差 RMS 9,560.96。不是 WAV header 变化或可忽略的低位误差，也不能用“长度相同”作为通过。

源码检查未发现明确的共享 prompt 或跨流交接问题；候选同时删除了同步等待和新的 GPU allocation，尚未确定差异首次出现于完整 embedding、码本生成还是解码。单纯 GPU clone 只恢复独立存储、不恢复同步等待，不能未经验证就当作修复。

因此停止候选多人压测，撤回模型变动并恢复原镜像，不宣称局部 2.6 ms 收益已转化为用户体验改善。未采用候选镜像 `06-fish-tts-vllm-omni:prefill-transfer-20260906`（ID `sha256:dbaef4303d7b604ccf8eec8199dc1b8020aa92a441a98e0cb5f8bb250189bccd`）仅留作实验备份，不应上线。

回退后容器为 running/healthy，镜像恢复 `06-fish-tts-vllm-omni:sampling-only-20260906`（ID `sha256:b3027985d5c5e3900d7bbcbbde77923781f606d84be3831dc1d7b37fd67faa24`）；`restored.wav` 与本轮 `baseline.wav` 逐字节一致，完成 A→B→A 复核。

## 原模型三轮稳态 HTTP 观察

每组使用相同 182 字输入、每用户独立固定种子，保留十个槽位、首包 4 帧、正常包 25 帧和 1.4 秒模拟播放缓冲。四路共 12/12、十路共 30/30 成功，全部模拟播放零断流。

| 并发 | 首音 P95，各轮范围 | 响应头 P95，各轮范围 | 响应头到首音 P95，各轮范围 | 聚合音频秒/墙钟秒，各轮范围 |
|---:|---:|---:|---:|---:|
| 4 | 0.327～0.338 s | 0.049～0.052 s | 0.278～0.287 s | 6.424～6.428 |
| 10 | 0.604～0.642 s | 0.128～0.165 s | 0.476～0.506 s | 10.946～12.481 |

各阶段 P95 来自独立的逐请求样本分布，不能把同一行两个 P95 相加当作整条首音 P95。当前等待大部分发生在响应头之后，但该区间仍混合排队、推理、编码和传输，不能据此直接认定是哪一个模型耗时。

四人最长共同连续模拟播放约 31.99 秒。上述结果是原模型基线，不是新优化的收益，不证明可以提升人数上限；也不包含重启后的首次编译等待。

### 回退后的首次十路预热，单独记录

`restored-warm10.json`：10/10 完成，模拟连续播放通过，但首音 P95 **8.578 秒**，响应头 P95 **0.180 秒**，逐样本响应头到首音 P95 **8.442 秒**。这是重启后首次十路记录，**不能混入上述稳态数据，也不能因播放不中断就说首音体验好**。它与现有首次运行编译/预热问题一致，但客户端两段时间不能单独证明每一毫秒来自编译。

后续比继续删除小算子更值得优先检验的方向是：真实生产形状预热是否完整，以及服务何时应宣告可承接用户请求。对于任何进一步省同步或缓存优化，需要记录完整推理的中间码本对照来定位本轮音频分歧，不能只看局部张量一致性。

### 恢复后的四／十用户应用播放与取消隔离

使用真实模型 HTTP、当前 FishTtsService 和进程内 SpeechWebSocketHub，合成多用户分句文本及接收端：

- 四人：4/4 完成，共同连续模拟播放 17.499 秒；取消一人后，其余 3/3 仍完成，PCM 隔离与容量释放通过。
- 十人：10/10 完成，共同连续模拟播放 17.554 秒；取消一人后，其余 9/9 仍完成，PCM 隔离与容量释放通过。
- 所有场景模拟播放间断数均为零；仍使用十路容量，没有放宽缓冲或验收阈值。

这不是多台真实浏览器或音频设备测试，不覆盖真实 WebSocket 网络、Redis、数据库、LLM、主观听感及长期负载。它只确认恢复后的已有模型路径在本轮合成场景下保持四／十用户连续播放与取消隔离，不能称为新并发上限。
