# Fish S2-Pro：采用采样去重，撤回 DAC 长度试验

本轮接续 [FastAR 编译路径修复](tts-fast-ar-compile-20260906.md)，保持原模型、权重、音色、精度、采样参数和十路容量。原试验包含采样去重及 DAC 长度元数据调整，最终只保留采样去重。

**当前结论：仅采用 softmax 去重，独立实现的固定请求完整 WAV 已与原基线逐字节一致，模型容器已加载该镜像并保持健康。** 两项组合候选曾未通过完整 HTTP 音频一致性检查，已经拒绝；DAC 长度补丁及对应测试已从仓库撤回，Dockerfile 已移除 DAC 接线，运行中的 DAC 保留原实现。

**正式十路 HTTP 吞吐为 12.2284 音频秒/秒，对比本轮基线 12.2119，仅 +0.135%，基本持平；首音没有改善，不能据此增加并发人数。** 以下微基准不代表等幅整链路提速，不得重复计算上一轮 eager→compiled 收益，也不能将采样与已撤回 DAC 的百分比相加。固定音频、正式 HTTP、四/十用户应用分句播放与取消隔离检查均已完成。

## 原组合试验的两个改动

1. **已采用的** [采样补丁](../fish_tts/patches/vllm_omni_0_24_fish_sampling.patch)：将 top-p 分支中相同 `sorted_logits` 的两次 softmax 合并为一次 `sorted_probs`，同时用于累加和阈值判断。top-p 开启时，每个残差码本步骤的 softmax 总调用从 3 次降到 2 次；排序、边界条件、掩码、scatter 和逐用户 multinomial 不变。top-p 关闭及 greedy 路径不变。
2. **DAC 长度补丁已撤回，不在当前仓库或 Dockerfile 中。** 原试验让支持 lengths 参数的 codec 将 `feature_lengths` 留在 CPU，以减少长度元数据的设备往返；波形仍使用原设备上的 codes，不支持 lengths 的兼容分支保留原设备。补丁没有直接改变精度、帧预算、分组或裁剪规则，但这不能证明完整链路必然等价。临时证据仍保存在 `/tmp/fish-dac-length-candidate.8eSazR/dac_cpu_lengths.patch`，不随仓库提交。

补丁继续由 Dockerfile 的固定源码哈希检查保护，不升级 vLLM-Omni 0.24.0、PyTorch 2.11.0+cu130 或 S2-Pro。

`fastar-comparison.json` 对比的两边都启用上一轮的正确编译路径。计时包含完整 FastAR、输出头和逐用户采样；各批量运行三轮，每轮交替执行两种实现，各取 50 次预热后样本的中位数。

| 1 | 12.133～12.172 ms | 12.071～12.095 ms | +0.52%～+0.63% |

这是亚百分比级小改进，四路有一轮轻微倒退，不能据此承诺用户明显感知提速。它不是端到端吞吐、首音或浏览器播放数据。

使用真实 FastAR 全部 27 个参数项和合成隐藏状态，三轮共 **42 批**检查覆盖批量 1～10、倒序用户、用户子集与缩批再恢复：候选与当前已编译基线的采样码本、所有用户 RNG 状态、已写 KV 均精确一致，两边均无编译失败。

强化后的 `verification.json` 另外记录：

- `1→10→2→9→3→8→4→7→5→6→1` 两轮，共 220 个位置检查点；hidden、logits、已写 KV 最大绝对误差均为 0。
- 2700 次编译路径调用对应 2700 次真实图执行，4 个图，0 次 graphless 调用；验证进程启用严格重编译上限检查。
- 验证器中的 eager/compiled 计时仅服务于正确性与编译覆盖检查，**不能替代上述 compiled/compiled 对照计算本轮收益**。

## CPU 采样与应用回归

真实 Torch CPU 矩阵 **216 组全部通过**：随机、全相等、分档 ties 三种 logits × FP32/BF16 × 批量 1/4/10 × top-k 0/1/30/1024 × top-p 0.01/0.9/1.0。

每组执行两轮持续使用的逐用户生成器，另检查用户顺序反转、共享生成器和 greedy。新旧实现的概率、掩码、采样码本及 RNG 推进精确一致；greedy 不消耗 RNG。该矩阵运行时显式隐藏 GPU，不证明 GPU 吞吐或主观音质。

组合试验阶段 CPU 自动化回归曾有 **86 项通过**；撤回 DAC 补丁及对应测试后，当前仓库 CPU 回归为 **82 项通过**，相关应用回归 **196 项通过**。这些不能替代真实 HTTP 音频与多用户播放验收。

## 已撤回的 DAC 试验：预热结果及未定位差异

`dac-lengths.json` 使用真实 FP16 DAC、原 `frame_length=2048` 和帧预算 256，覆盖批量 1/4/10 × 首包 4 帧、普通 25 帧、带 4 帧上下文的 29 帧、带 25 帧上下文的 50 帧、混合尾包，共 **15 种组合**。

每个组合、每种实现预热三次后，各测 20 次；完整波形、返回长度、上下文裁剪后波形及预期输出尺寸均精确一致，预热后的基线自重复也一致。各组合中位数速度比为 **1.0015～1.0125×**，仍是小收益。例如十路稳态带上下文分组为 `5+5`，中位数从 89.132 ms 降至 88.592 ms；未扩大帧预算来凑收益。

**冷首包有一个尚未定位的差异，不能被预热通过覆盖。** 最初未预热的单用户 4 帧对比中，长度及输出尺寸相同，但完整及裁剪波形未精确一致，最大绝对差为 **0.000335693359375**。由于当时没有记录冷态基线自重复，现有证据不能判断原因是补丁、首次执行状态还是其他因素，也不能保证冷启动逐点一致。没有放宽容差让这一结果通过；原失败独立保存在 `dac-cold-initial-failed.json`。

上述是独立真实 DAC 的完整分组 forward，不是 HTTP/浏览器 SLA；预热状态的逐点一致不等于所有输入及冷态的音质验证。

候选三次结果彼此一致，却持续不同于原基线；重启恢复基线后又精确回到原基线 WAV。因此不能把候选差异仅归为第一次冷调用。组合候选没有满足本轮“输出保持不变”的验收标准，当时已拒绝并恢复基线。后续仅保留 softmax 的隔离试验没有重现该差异，见下一节；这不等于已经定位 DAC 冷态差异的内部原因，更不能称 DAC 冷态问题已修复。

组合候选启动后的十路预热轮 `candidate-warm10.json` 虽然 **10/10** 完成、模拟播放没有中断，但首音 P95 为 **8.6565 秒**。这是冷/首次十路预热记录，不混入稳态性能比较，也不能以“无断流”掩盖较长起播等待。该组合没有继续运行正式三轮吞吐对照或宣布最终通过。

采用镜像标签为 `06-fish-tts-vllm-omni:sampling-only-20260906`，只保留 softmax 去重。**本轮仅更新 Fish 模型容器，`TTS_ENABLED=false` 始终未改，没有自动开启全站语音。** 四/十用户应用分句播放及取消隔离结果：

固定 WAV 和真实 HTTP 加模拟播放检查，不替代实际多台浏览器、真实 WebSocket 网络、音频设备或长时稳定性验收。
