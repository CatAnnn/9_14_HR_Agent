# Fish S2-Pro 继续调优：批处理收益与连续播放边界

本轮承接 [八路测试](tts-throughput-20260906.md)，仍使用原 Fish S2-Pro 权重、vLLM-Omni 0.24.0、固定合成音色、独立 GPU 1（49,140 MiB）。没有更换模型、减少文本、改变语速、采样或音频精度。

## 本轮采用十路

最终选择 **Stage 0 / Stage 1 = 10、DAC 帧预算 256、应用本地/全局名额 10**。长文本总音频吞吐从 10.777 增至 **11.939 音频秒/墙钟秒（+10.78%）**；测试并发从八路增至十路（+25%）。这是容量与总吞吐提升，不是单个用户生成更快：满载首音最慢从 0.538 秒升至 0.752 秒，RTF 最慢从 0.728 升至 0.838。

十用户真实应用内分句播放连续执行三轮，正常场景 **30/30 完成、零模拟断流**，各轮最长共同连续播放 **17.426 / 17.366 / 17.461 秒**。三次取消测试中，其余 **27/27 用户**在同伴取消后继续收到音频并完成，音频隔离、容量释放和缓冲等待探针均通过。

新配置下原八路直连回归 **24/24**，吞吐 10.694、相对基线 -0.77%，处于本次轮间波动范围，未观察到明显退化。原四用户分句播放及取消也通过，共同连续播放 **17.461 秒**。

最终相关自动化回归 **328 项全部通过（29.71 秒）**，覆盖语音分句、缓冲、取消、隔离、容量边界、协调及相关工作流；Compose 配置检查和相关文件 `git diff --check` 通过。真实负载结束后已停止 GPU 采样，网站及模型服务健康。

十路是当前固定工作负载下通过的运行点，不是最大容量或生产 SLA。十二路仅保留测试入口及配置校验上限用于受控实验，不能据此认定十二路播放合格。

## 对照实验

使用相同 182 字合成正文及逐请求编号，固定种子；直连每组预热后三轮，token 上限 2048。网站分句仍为原 1024 上限，两个工作负载不能混算。吞吐是合计音频秒除以三轮各自整轮墙钟时间之和，不是把每个请求的延迟相加，也不是请求数/秒或单用户提速。

| 模型两阶段容量 | DAC 帧预算 | 同时请求 | 成功数 | 总音频吞吐 | 最慢首音 | 最慢 RTF |
|---|---:|---:|---:|---:|---:|---:|
| 8 / 8（本轮基线） | 256 | 8 | 24/24 | 10.777 | 0.538 秒 | 0.728 |
| 8 / 8 | 512 | 8 | 24/24 | 10.645 | 0.833 秒 | 0.731 |
| 10 / 10（采用） | 256 | 10 | 30/30 | 11.939 | 0.752 秒 | 0.838 |
| 12 / 12 | 256 | 12 | 36/36 | 13.273 | 1.004 秒 | 0.903 |

各组直连均无模拟播放中断，但这不能代替分句应用测试。RTF 为每个请求合成耗时除以其音频时长，越小实时余量越大。这里的“最慢首音”不含 LLM、业务排队或浏览器 1.4 秒起播缓冲。

### 不采用 DAC 512

实际 DAC 按 `批量 × 最大帧数` 拆组；512 可以容纳更多已就绪请求，不等待凑批，也不修改 token 或裁剪规则。但实测吞吐相对 256 为 -1.22%，两组三轮区间重叠，不能证明收益；首音也没有改善。因此恢复 **256**，不扩大单次解码负载。

### 不采用十二路作为默认值

十二路直连总吞吐比八路高 23.17%，但每路 RTF 与首音均变大。真实 Fish HTTP 加应用分句、逐流播放反馈及内存接收端测试中：

- 十二用户都完成了音频传输、隔离哈希匹配，取消一人后其余十一人也继续收到音频并完成。
- 正常播放中两用户分别出现 **1.407 秒、1.409 秒** 模拟重缓冲。
- 所有用户最长共同播放虽有 14.26 秒，但不能掩盖个别用户断流，因此整体判定不通过。

没有把起播缓冲从 1.4 秒加大，也没有放宽 0.1 秒中断与共同连续播放至少 10 秒的标准来获得“通过”。十路按相同标准验证后采用。

## 验证范围

本轮是实际 GPU、真实模型 HTTP 和合成用户接收端测试，不是多台浏览器实测。应用测试包含真实 `FishTtsService` 和 `SpeechWebSocketHub`，但不包含 Redis、数据库、LLM、真实 WebSocket 网络或音频设备；PCM/哈希不证明朗读语义、无静音或主观音质。测试使用固定合成文本而非真实用户数据，未执行长时稳定性或多模型同时繁忙压力测试。

十路直连 GPU 1 峰值显存 **24,019 MiB**，平均利用率 86.33%，最高 63°C；十二路为 24,009 MiB、88.33%、63°C。GPU 0 采样利用率为 0%。GPU 记录在基线测试开始后才启动，仅覆盖基线后约 39 秒，不作为完整基线峰值对照。

## 生效状态

- Fish 模型容器已经加载十路配置；`.env`、默认值及 Compose 的应用本地/全局名额同步为 10。
- **`TTS_ENABLED=false` 不变，未自动开启网站语音。** 测试只在独立进程内开启 TTS，不创建数据库会话。
- 未重建后端；当前后端启动环境仍保留旧名额，新的 10 路应用名额在下次正常重建后端时生效。模型参数已生效与网站开关/后端名额生效是不同事项。
- 未更改 ASR、embedding、reranker、模型镜像、权重或用户的其他代码变更。

## 原始记录与复现

本机 `loadtests/results/fish-tuning-20260906.VLjnsM/` 保存 JSON、`gpu.csv` 和逐候选 YAML，目录被 Git 忽略，不随代码提交：

- `baseline8-cap256.json`、`candidate8-cap512.json`、`candidate10-cap256.json`、`candidate12-cap256.json`：直连原始结果。
- `pipeline12-cap256.json`：十二用户分句播放失败及取消成功的完整记录。
- `pipeline10-r1.json`、`pipeline10-r2.json`、`pipeline10-r3.json`：三轮十用户分句播放和取消测试。
- `regression8-stage10.json`、`pipeline4-stage10.json`：十路配置下原八路直连及原四用户应用回归。
- `stage*-cap*.yaml`、`experiment.json`：实验参数；YAML 快照的说明注释沿用起测版本，以其中参数为准。
- `warm*-cap*.json`：不计入正式吞吐的预热结果。

直连复现沿用 `scripts/benchmark_fish_tts.py`，通过 `--concurrency`、`--rounds 3`、`--text-file loadtests/data/tts/sustained-reply.zh.txt`、`--max-new-tokens 2048` 和 `--require-continuous-playback --min-common-playback-seconds 10` 测试。应用内复现用 `python -m scripts.benchmark_fish_pipeline --url http://fish_tts:8091/v1/audio/speech --concurrency N --slots N --scenario both --require-continuous-playback --min-common-playback-seconds 10`，需在安装了项目依赖且能访问模型的环境中执行。

## 未直接启用的优化

源码还显示 FastAR 的编译对象为 `model.forward`，实际残差循环却调用 `model.forward_one`；仅看到编译日志不能认定热路径已编译。改接编译热路径需单独验证 KV 原地写入、位置切片、动态批量与采样生成器状态，本轮不混入该高风险变化。逐请求 RNG、现有 CUDA Graph 安全约束与前缀缓存设置均保留。

后续已单独处理这一编译路径，过程与验证见 [FastAR 编译修复](tts-fast-ar-compile-20260906.md)；不要把后续编译收益与本报告的批量调优收益混算。
